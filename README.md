# Альфа-Бизнес · персонализированные бизнес-инсайты

Приложение собирает новости и банковскую аналитику, сопоставляет их с профилем компании и формирует инсайты для финансового директора и казначея. В статье можно посмотреть источники, сохранить материал, поставить оценку и задать уточняющий вопрос по её содержанию.

Стек: **React + TypeScript + MobX + Ant Design + Sass**, **FastAPI + SQLAlchemy + SQLite**, **Sentence Transformers + FAISS**, внешняя **LLM через API**.

## Быстрая проверка на синтетических данных

Для проверки без закрытых материалов и API-ключа выполните из корня репозитория:

```sh
sh scripts/start.sh synthetic
```

Нужны запущенный Docker с Compose **2.20 или новее**, свободный порт `8081` и интернет для первой сборки образов и установки пакетов. После сборки синтетическому конвейеру внешние сервисы не нужны. API работает на CPU; на Apple Silicon для `linux/amd64` нужна эмуляция. Практический стартовый ориентир для Docker — 4 CPU, 8 ГБ RAM и 15 ГБ свободного диска; это рекомендация, а не измеренный минимальный порог.

Скрипт запускает отдельный Compose-проект `alfa-synthetic`, ждёт готовности API и web, затем выполняет HTTP-проверку через nginx. При успехе в терминале появятся строки `PASS` для обоих аккаунтов. Откройте [синтетический стенд](http://127.0.0.1:8081/), войдите как Анна или Илья, откройте одну из пяти статей, проверьте источники, сохранение и чат. Пароли не нужны: используются демонстрационные аккаунты `anna` / `cfo` и `ilya` / `treasury_head`. Компания для сценария — `U_900001`.

**Это сквозная проверка приложения с заменами внешних ML-компонентов.** CSV preprocessing, управление конвейером, проверка цитат, Markdown, публикация, SQLite, HTTP API и интерфейс настоящие. Сбор публикаций/PDF, нейронное ранжирование и ответы LLM воспроизводятся из тестовых фикстур. Статьи и чат явно помечены как синтетические. Этот тест не доказывает качество моделей, OCR или доступность внешнего шлюза. Для живого ML используйте раздел 1 ниже.

Три вымышленных профиля и десять вымышленных источников входят в [`demo/fixtures`](demo/fixtures). Стенд не читает закрытые входные данные и использует отдельные Docker-тома. Полный [сценарий приёмки и границы теста](docs/ACCEPTANCE.md), [описание фикстур](demo/README.md) и [реестр состава поставки](docs/DELIVERY.md) включены в репозиторий.

```sh
# Повторить HTTP-проверку и публикацию, не пересобирая контейнеры.
docker compose -f compose.synthetic.yaml exec -T api python -m demo.verify --base-url http://web:8080
# Остановить синтетический стенд, сохранив данные.
docker compose -f compose.synthetic.yaml down
```

Для другого порта: `SYNTHETIC_PORT=8082 sh scripts/start.sh synthetic`. Скрипт не создаёт и не перезаписывает `.env` в синтетическом режиме.

## 1. Локальный запуск бэкенда и ML по шагам

Команды выполняются из корня репозитория в Bash/Zsh на macOS, Linux или в WSL на Windows. Docker запускает фронтенд, API и Python-модули; отдельно устанавливать Python, Node.js и OCR на компьютер для этого способа не требуется.

### Шаг 1. Подготовьте окружение

Установите и запустите Docker Desktop либо Docker Engine с Compose 2.20 или новее. Откройте терминал в папке проекта и выполните:

```sh
docker version
docker compose version
```

В `docker version` должны быть доступны и Client, и Server. Если сервер недоступен, запустите Docker и повторите проверку. Нужны свободный порт `8080` и доступ к реестрам контейнеров, пакетам, Hugging Face, источникам публикаций и API модели.

API собирается для `linux/amd64`; на Apple Silicon используется эмуляция. Первая сборка и загрузка моделей могут занять продолжительное время. Веса моделей не входят в репозиторий, GPU для текущей конфигурации не нужен.

### Шаг 2. Создайте файл настроек

```sh
# Выполняйте копирование только при первом запуске, если .env ещё нет.
cp .env.example .env
mkdir -p inputs/csv parser/inputs/analytics
```

Откройте `.env` в редакторе. Для живой генерации заполните:

```dotenv
ALPHA_LLM_BASE_URL=https://api.alfahack-gateway26.ru/v1
ALPHA_LLM_API_KEY=ВАШ_API_КЛЮЧ
ALPHA_LLM_MODEL=ТОЧНЫЙ_ID_МОДЕЛИ
ALPHA_LLM_FAMILY=GLM-5.3-Flash
```

`ALPHA_LLM_BASE_URL` — адрес совместимого шлюза; в примере указан адрес из конфигурации проекта. `ALPHA_LLM_API_KEY` — ключ доступа к этому шлюзу. `ALPHA_LLM_MODEL` — точный идентификатор доступной модели, а не произвольное название. `ALPHA_LLM_FAMILY` задаёт семейство и не заменяет ID модели. Используйте выданные для выбранного провайдера значения.

Ключ применяется только на сервере. Не помещайте его в `VITE_*`, клиентский код или Git. Без ключа приложение откроется с подготовленными статьями, но генерация и живой чат работать не будут.

В `.env.example` разрешены запросы при неизвестной стоимости: `ALPHA_ALLOW_UNKNOWN_COST=true`. Для учёта бюджета заполните `ALPHA_INPUT_RUB_PER_MILLION` и `ALPHA_OUTPUT_RUB_PER_MILLION` по тарифам шлюза и установите `ALPHA_ALLOW_UNKNOWN_COST=false`. Без тарифов `ALPHA_DAILY_BUDGET_RUB=500` не обеспечивает жёсткий лимит расходов.

### Шаг 3. Добавьте исходные данные

Разместите CSV компаний и аналитические PDF в этих папках:

```text
inputs/
  csv/
    df_Uid_data_hack.csv
parser/
  inputs/
    analytics/
      ALFA-7M26.pdf
      ALFA-consumption.pdf
      ...
```

Полный список имён PDF находится в [`parser/config/analytics_manifest.json`](parser/config/analytics_manifest.json), в поле `documents[].file`. Имена файлов должны совпадать с манифестом, включая регистр и кириллицу.

CSV и PDF не входят в Git: добавьте их из исходных материалов проекта. CSV должен соответствовать схеме preprocessing; идентификатор исходной компании хранится в `SYNTHETIC_U`. Пустой файл или произвольная таблица вместо датасета не подходят. На шаге 7 получите ID уже после очистки данных.

### Шаг 4. Соберите и запустите приложение

```sh
docker compose --profile search config --quiet
sh scripts/start.sh live
docker compose --profile search ps
```

Скрипт запускает три сервиса в одном Compose-проекте:

- `api` — FastAPI, preprocessing, парсер, ранкер, генератор и Tesseract OCR;
- `web` — собранный React-клиент и nginx, который перенаправляет `/api` в `api:8000`;
- `searxng` — веб-поиск, доступный API по внутренней сети Docker без ручного подключения контейнеров.

Дождитесь готовности сервисов. Проверяйте запуск командой:

```sh
docker compose logs --tail=100 api web
```

### Шаг 5. Проверьте файлы и настройки модели

```sh
curl -fsS http://127.0.0.1:8080/api/parser/health
curl -fsS http://127.0.0.1:8080/api/insight-agent/health
```

Во втором ответе ожидаются `"status":"ok"` и `"llm_configured":true`. Это проверка заполнения настроек; реальную доступность модели проверяет генерация на шаге 8.

Проверьте, что контейнер видит исходные файлы:

```sh
docker compose exec -T api python - <<'PY'
import json
from pathlib import Path

csv = Path('/app/inputs/csv/df_Uid_data_hack.csv')
print('CSV:', 'OK' if csv.is_file() else 'НЕ НАЙДЕН', csv)
manifest = json.loads(Path('/app/parser/config/analytics_manifest.json').read_text())
for item in manifest['documents']:
    path = Path('/app/parser/inputs/analytics') / item['file']
    print('PDF:', 'OK' if path.is_file() else 'НЕ НАЙДЕН', item['file'])
PY
```

Если меняли `.env` после запуска, пересоздайте API и повторите health-запрос:

```sh
docker compose up -d --force-recreate api
```

### Шаг 6. Проверьте веб-поиск

SearXNG уже запускается командой `sh scripts/start.sh live` в профиле `search`. В `.env` для него используется `ALPHA_SEARXNG_URL=http://searxng:8080`; отдельный порт на хосте не публикуется. Ручная команда `docker network connect` больше не нужна.

```sh
docker compose exec -T api python -c 'import httpx; r = httpx.get("http://searxng:8080/search", params={"q": "экономика", "format": "json"}, timeout=30); r.raise_for_status(); print("Результатов поиска:", len(r.json().get("results", [])))'
```

Если поиск ещё запускается, проверьте `docker compose --profile search logs --tail=100 searxng` и повторите проверку. Пустой список подтверждает HTTP-доступ, но не получение полезных источников.

Для существующего внешнего SearXNG задайте его адрес в `ALPHA_SEARXNG_URL` и запускайте `docker compose up --build --wait`, без профиля `search`. URL должен быть доступен из контейнера `api`. Без рабочего поиска RSS и PDF доступны, но полнота сбора не гарантируется. `parser/compose.yaml` сохранён для самостоятельной разработки парсера; для общего запуска он не требуется.

### Шаг 7. Выберите компанию и войдите в интерфейс

Выведите первые 20 ID из очищенного датасета:

```sh
docker compose exec -T api python - <<'PY'
from preprocessing import preprocess_csv

result = preprocess_csv('/app/inputs/csv/df_Uid_data_hack.csv')
for company in result['companies'][:20]:
    print(company['company_id'], company.get('industry'), company.get('region'))
PY
```

Скопируйте нужный `company_id`. ID тестового пользователя и ID компании — разные значения.

Откройте [локальное приложение](http://127.0.0.1:8080/) и выберите аккаунт:

| Аккаунт | ID пользователя | Роль для ML |
| --- | --- | --- |
| Анна Смирнова | `anna` | `cfo` — финансовый директор |
| Илья Воронов | `ilya` | `treasury_head` — казначей |

[Swagger API](http://127.0.0.1:8080/docs) доступен по тому же адресу на `/docs`.

До первой генерации оба аккаунта видят общую подборку из трёх подготовленных статей. Вход в аккаунт сам по себе не запускает ML.

### Шаг 8. Запустите настоящий ML-конвейер

Создайте в корне проекта `request.json`, заменив `COMPANY_ID` на ID из шага 7:

```json
{
  "action": "run",
  "audience_type": "cfo",
  "company_id": "COMPANY_ID",
  "allow_pdf_processing": true
}
```

`allow_pdf_processing: true` разрешает первичное извлечение текста и OCR из PDF. Без этого флага пайплайн рассчитывает на ранее подготовленный PDF-кэш.

Выполните запрос для Анны:

```sh
curl --fail-with-body -sS -X POST http://127.0.0.1:8080/api/pipeline/run \
  -H 'Authorization: Bearer anna' \
  -H 'Content-Type: application/json' \
  --data-binary @request.json \
  -o pipeline-response.json
cat pipeline-response.json
```

Токены `anna` и `ilya` подходят для стандартного локального запуска с демоавторизацией. `POST /api/auth/login` возвращает тот же ID как `access_token`; кода доступа и подписанных сессий в текущем API нет.

Запрос последовательно выполняет подготовку профиля, сбор источников, ранжирование и генерацию. При первом обращении ранкер может скачивать веса. В другом терминале можно смотреть ход выполнения:

```sh
docker compose logs -f --tail=100 api
```

Проверьте ответ в `pipeline-response.json`:

- `published_insight_ids` — непустой список ID опубликованных статей;
- `status: completed` — выполнение завершено; `partial` — есть ограничения или неполный результат, изучите `gaps`, `errors` и `stop_reason` в ответе;
- при ошибке HTTP её описание находится в `detail`, сведения о сбое конвейера — в `detail.error`.

Генератор по умолчанию запрашивает минимум пять проверенных инсайтов. Их количество зависит от найденных материалов и прохождения валидации; наличие ключа не гарантирует результат. Если `published_insight_ids` пуст или отсутствует, новая подборка не опубликована.

Для Ильи измените `audience_type` в `request.json` на `treasury_head` и повторите запрос с `Authorization: Bearer ilya`. Роль в запросе должна совпадать с ролью аккаунта. Обе подборки создаются отдельными вызовами.

### Шаг 9. Проверьте статьи и живой чат

Обновите страницу приложения под тем аккаунтом, для которого запускали генерацию. Откройте одну из новых статей и задайте вопрос, например: «Какие источники подтверждают главный вывод и что проверить в компании?»

У опубликованного ML-инсайта есть сохранённый контекст и блок чата. У исходных общих статей его нет — даже при заполненном API-ключе.

Для проверки чата через API возьмите ID из `published_insight_ids` и замените `INSIGHT_ID`:

```sh
curl --fail-with-body -sS -X POST http://127.0.0.1:8080/api/insights/ask \
  -H 'Authorization: Bearer anna' \
  -H 'Content-Type: application/json' \
  -d '{"insight_id":"INSIGHT_ID","question":"Какие источники подтверждают главный вывод?","history":[]}'
```

Ожидается ответ с непустыми `paragraphs` и `generation_method: ai`. Для подборки казначея используйте `Bearer ilya`. Успешная генерация и этот ответ подтверждают работу живой модели; один health-запрос этого не подтверждает.

### Шаг 10. Остановите или перезапустите приложение

```sh
# Остановить приложение, сохранив базу, модели и результаты.
docker compose --profile search down

# Запустить снова.
docker compose --profile search up --wait

# Пересобрать после изменения кода.
sh scripts/start.sh live
```

Не используйте `docker compose down -v` для обычного перезапуска: эта команда удаляет тома с данными. SearXNG в профиле `search` останавливается вместе с приложением.

### Если запуск не удался

| Симптом | Что проверить |
| --- | --- |
| Docker не подключается к серверу | Запущен ли Docker Desktop/Engine; доступен ли Server в `docker version` |
| Порт `8080` занят | Задайте другой `APP_PORT` в `.env`, повторите `docker compose up -d` и используйте этот порт во всех адресах |
| `llm_configured: false` | Три значения `ALPHA_LLM_BASE_URL`, `ALPHA_LLM_API_KEY`, `ALPHA_LLM_MODEL`; пересоздание API после изменения `.env` |
| Ошибка ключа или модели при генерации | Доступ ключа к шлюзу, точный ID модели, лимит и баланс на стороне провайдера |
| CSV не найден или компания отсутствует | Путь файла, схема CSV, ID после preprocessing из шага 7 |
| Нет PDF/источников или `partial` | Имена файлов из манифеста, `allow_pdf_processing`, доступность RSS и SearXNG; поля `gaps` и `errors` |
| Ошибка скачивания моделей | Доступ из контейнера к Hugging Face и свободное место для кэша |
| `403` при генерации | Соответствие токена аккаунта полю `audience_type` |
| Новые статьи не появились | Непустой `published_insight_ids`, выбранный аккаунт, обновление страницы |
| В статье нет чата | Открыт ли новый ML-инсайт, а не одна из исходных общих статей |
| Долгий запрос завершился `504` | Логи `api`: nginx ждёт ответ до 600 секунд; обработка в API могла продолжиться. Проверьте ленту и результаты перед повторным запуском |

## 2. Сайт на Netlify

**Сайт: https://alfa-hack.netlify.app/#/.**

Статическая версия показывает два аккаунта и по две редакционно подготовленные статьи с разным акцентом для финансового директора и казначея. В статьях есть проверенные факты из обзора worldsteel, расчёты по синтетическому плану закупок, ссылки на источники и исходные девять строк плана. Сохранение и оценки работают в браузере отдельно для каждого аккаунта. Реальный ML-конвейер и чат в этой версии не запускаются.

Полный сценарий с настоящим ранжированием, генерацией и чатом доступен при локальном запуске по инструкции выше: добавьте исходные данные, настройте API модели, выполните генерацию и откройте опубликованные статьи. Банковские остатки и задачи на главной остаются демонстрационными и локально.

Корневой [`netlify.toml`](netlify.toml) уже собирает именно эту версию: базовая папка `client`, команда `npm run build:demo`, каталог публикации `dist`. Переменные окружения в Netlify для неё не нужны. Обычный `npm run build` остаётся связанным с локальным FastAPI.

## 3. Архитектура и техническое устройство

### Общая схема

```text
Браузер: React SPA
        │ HTTP /api, Bearer-токен
        ▼
nginx: статика, проксирование API
        │
        ▼
FastAPI ────────────────────────────── SQLite
        │                              пользователи, статьи, ML-контекст,
        │                              сохранения, оценки, вопросы
        ▼
backend.py / InferenceService
        │
        ├─ preprocessing: CSV → профиль и признаки компании
        ├─ parser: RSS / веб-поиск / PDF / OCR → ranking_input
        ├─ ranking_module: отбор и ранжирование → sets[]
        ├─ pipeline_adapter: наборы + исходные цитаты → вход генератора
        └─ insides: внешняя LLM → валидация → JSON и Markdown
                                                   │
                                                   ▼
                                       публикация в SQLite → лента роли
```

Это модульный монолит: модули обработки вызываются внутри Python-процесса, без HTTP между этапами. В базовом Compose два контейнера — `web` и `api`; профиль `search`, включаемый скриптом живого запуска, добавляет SearXNG в ту же сеть. LLM вызывается по внешнему API, модели ранжирования работают локально на CPU. Отдельной очереди задач и фонового ML-воркера нет: запуск конвейера выполняется синхронным API-запросом.

### Фронтенд

React SPA на TypeScript, сборка Vite, состояние MobX, компоненты Ant Design, иконки Lucide и стили Sass. Структура основана на Feature-Sliced Design:

| Слой | Назначение |
| --- | --- |
| `client/src/app` | Инициализация, провайдеры, роутер, общие стили и синхронизация состояния при смене пользователя |
| `pages` | Страницы входа, главной, подборки, статьи и заглушек разделов |
| `widgets` | Оболочка банка, боковое меню, сводка и карточки |
| `features` | Вход/выход, сохранение, оценка, копирование, ссылка на статью, источники и чат |
| `entities` | Сессия, инсайты, API-адаптеры, MobX-хранилища и модели данных |
| `shared` | HTTP-клиент, маршруты, Markdown, общие UI-компоненты и стили |

Импорты между слайсами проходят через публичные `index.ts` и направлены в нижележащие слои. Правила проверяет `client/scripts/check-architecture.mjs`.

Hash-маршруты: `#/`, `#/insights`, `#/insights/{id}`. HTTP-клиент использует `VITE_API_URL`; в разработке Vite перенаправляет `/api` на `VITE_PROXY_TARGET`, по умолчанию `http://127.0.0.1:8000`. API-адаптер преобразует серверный `snake_case` в поля интерфейса. Ошибки API показываются пользователю.

Токен сессии хранится в `sessionStorage`. В режиме API сохранения и оценки находятся в SQLite; в статическом демо — в `localStorage`. При `VITE_DEMO_MODE=true` HTTP заменяется адаптером `client/src/shared/api/static-demo.ts`.

Статьи отображаются через `react-markdown` и `remark-gfm`: заголовки, списки, таблицы и ссылки на источники. Сырой HTML и опасные URL не исполняются. Обложка определяется категорией инсайта; предложение банковского продукта отображается отдельным блоком, если оно есть. Чат передаёт последние пять обменов репликами; история в интерфейсе сбрасывается при уходе со страницы.

### Бэкенд и хранение

Точка входа — `server/app/main.py`, веб-сервер — Uvicorn. FastAPI принимает запросы, Pydantic проверяет входные данные, SQLAlchemy работает с SQLite. При запуске создаются таблицы, обновляются поддерживаемые поля старой схемы и добавляются стартовые данные.

Роутеры разделены по назначению: `auth`, `insights`, `preferences`, `parser`, `ranking`, `agent`, `pipeline`. `backend.py` управляет последовательностью ML-этапов, `server/app/publication.py` сохраняет принятые статьи и исходный ML-контекст.

Основные сущности БД: пользователи, компании, статьи и секции, план закупок, пользовательские настройки, история вопросов, запуски/материалы/наборы ранжирования и `GeneratedInsight`. Последняя хранит исходный JSON генерации, роль, компанию и ID запуска; этот контекст используется в чате.

Роль определяется сервером по аккаунту. Генерация для `anna` требует `cfo`, для `ilya` — `treasury_head`. Лента выбирает результаты своей роли; пока их нет, показывает общие статьи. Прямая ссылка на статью может открываться и под другим аккаунтом: разделение лент не является полноценной изоляцией данных компаний.

Стандартный локальный вход — демонстрационный, токен равен ID аккаунта. Пароли, коды доступа и подписанные сессии не реализованы. `ALPHA_DEMO_ACCESS_CODE`, `ALPHA_SESSION_SECRET` и `ALPHA_CORS_ORIGINS` сервер не обрабатывает. CORS разрешён для `localhost:5173` и `127.0.0.1:5173`; Docker-интерфейс работает через nginx на том же origin. Это локальный прототип, а не промышленная система авторизации.

### Preprocessing: подготовка компаний

`preprocessing/` читает CSV, проверяет обязательные столбцы, обрабатывает пропуски и дубликаты, нормализует идентификаторы и рассчитывает признаки компаний. Групповые показатели вычисляются по всему очищенному датасету до выбора конкретной компании. Результат — JSON `company_profiles` с профилем, атрибутами и признаками.

Кэш зависит от содержимого CSV, разделителя и версии кода. Изменение исходных данных приводит к пересчёту. При полном запуске ранкер получает тот же очищенный датасет, чтобы ID и признаки совпадали между этапами.

### Парсер: сбор новостей, аналитики и конкурентов

`parser/src/alpha_parser/` — собственный Python-модуль сбора данных. Точка доступа — `ResearchModule`.

- **Новости:** HTTP-загрузка через `httpx`, RSS/Atom через `feedparser`, извлечение основного текста HTML через `trafilatura`.
- **Веб-поиск:** SearXNG; URL задаётся в `ALPHA_SEARXNG_URL`. Конфигурация источников находится в `parser/config/sources.json`.
- **Конкуренты:** подбор компаний для наблюдения и сбор связанных публикаций с учётом профиля клиента.
- **Аналитика:** PDF из явного манифеста; `pdfplumber`/`pdfminer.six` извлекают текст и таблицы, PDFium рендерит страницы, Tesseract распознаёт сканы на русском и английском.
- **Происхождение данных:** сохраняются ID и версии документов, фрагменты, страницы, URL, даты, качество извлечения и ограничения сбора.

На выходе — `ranking_input`: профиль компании, материалы по темам, список наблюдения и метаданные источников. Недостающие документы и проблемы извлечения отражаются в диагностике. Параметр `cached_only` ограничивает сбор подготовленным кэшем.

### ML: ранжирование материалов

`ranking_module/src/alfa_insights/` использует предобученные модели; обучение с нуля при запуске не выполняется. Настройки находятся в `ranking_module/config.yaml`.

| Компонент | Реализация |
| --- | --- |
| Векторные представления | `intfloat/multilingual-e5-small` через Sentence Transformers |
| Поиск похожих материалов | FAISS по подготовленным индексам |
| Повторное ранжирование пар «профиль — текст» | `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` |
| Правила соответствия | Упоминания компании, алиасов и домена; отрасль, регион и другие признаки |
| Итоговая оценка по умолчанию | `0.4 × dense + 0.4 × cross + 0.2 × hard` |
| Выполнение | CPU; seed `42`, настройки детерминированности в конфигурации |

Если FAISS-индексов нет, предусмотрен отбор текущих материалов с cross-encoder. Индексы для большого корпуса можно подготовить скриптами в `ranking_module/scripts/`.

Результат — до 10 наборов `sets[]`: компания наблюдения, 2–5 новостей, 1–3 аналитических материала, оценки и причины отбора. Достаточное число наборов зависит от входных данных. `pipeline_adapter.py` восстанавливает исходные тексты и цитаты по ID, сохраняет границы наборов и отклоняет неизвестные ID или изменённые тексты.

### Генерация инсайтов и чат

`insides/` получает отобранные материалы, профиль и роль читателя. LLM планирует связанные события и пишет статьи; код проверяет структуру, цитаты, признаки компании, допустимые источники и продуктовые рекомендации. Проверки ограничивают ошибки, но не доказывают истинность каждого вывода модели.

Инсайт содержит выжимку, события, совместный вывод, основания, источники, Markdown и категорию `1–10`. Каталог `insides/alfa_products.json` используется только для подходящих рекомендаций: допустимо ноль продуктов, максимум — три. ID и цитата возможности проверяются, название и URL подставляются из каталога. Контракт результата — `insides/output.schema.json`.

Для чата сервер извлекает сохранённый `GeneratedInsight`, добавляет роль и историю вопросов, вызывает LLM и возвращает ответ со ссылками на документы. Общие стартовые статьи не содержат такого контекста. Вопросы и ответы сохраняются в БД; API восстановления полной истории для интерфейса пока нет.

### Основные API-методы

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/auth/users` | Список демонстрационных аккаунтов |
| `POST /api/auth/login`, `GET /api/auth/me` | Вход и восстановление сессии |
| `GET /api/insights`, `GET /api/insights/{id}` | Лента роли и статья |
| `GET /api/insights/meta/categories`, `GET /api/insights/meta/sources` | Категории и источники |
| `GET /api/insights/meta/profile`, `GET /api/insights/meta/purchase-plan` | Профиль и доступные данные закупок |
| `GET /api/insights/export/purchase-plan.csv` | Выгрузка плана закупок |
| `GET /api/preferences` | Сохранения и оценки пользователя |
| `POST /api/preferences/{id}/toggle`, `POST /api/preferences/feedback` | Изменение сохранения и оценки |
| `POST /api/pipeline/run` | Конвейер целиком или отдельные этапы через `action` |
| `POST /api/parser/collect`, `POST /api/parser/pdf` | Отдельный сбор источников и обработка PDF |
| `POST /api/ranking/validate`, `POST /api/ranking/run` | Проверка входного JSON и запуск ранкера |
| `GET /api/ranking/runs/{run_id}` | Сохранённый результат отдельного запуска ранкера |
| `POST /api/insight-agent/generate` | Генерация из подготовленных материалов и публикация |
| `POST /api/insights/ask` | Чат по сохранённому инсайту |
| `GET /api/parser/health`, `GET /api/ranking/health`, `GET /api/insight-agent/health` | Диагностика модулей |

Полные схемы тел запросов и ответов доступны в Swagger. В `POST /api/pipeline/run` поддержаны `collect`, `rank`, `generate`, `run`. Для `rank` и `generate` передаётся готовый `ranking_input`; `generate` может также принимать `ranking_result`. Полный сценарий запускается с `action: run`.

### Кэш, артефакты и Docker-тома

| Том | Данные внутри контейнера |
| --- | --- |
| `backend-data` | SQLite в `/app/state/backend.db` |
| `pipeline-cache` | Подготовленные данные и кэши в `/app/cache` |
| `pipeline-output` | Артефакты запусков в `/app/output` |
| `model-cache` | Hugging Face в `/app/.cache/huggingface` |
| `ranking-cache`, `ranking-runs`, `ranking-models` | Индексы, результаты и рабочие файлы ранкера |

`inputs/` и `parser/inputs/` подключаются с хоста только для чтения. Артефакты полного конвейера находятся в `/app/output/runs/<tenant_hash>/<run_id>/`: параметры запроса, preprocessing, источники, вход и выход ранкера, `06_insights.json`, статьи и источники в Markdown. Поле `artifacts` в ответе содержит пути внутри контейнера.

Скопировать результаты на компьютер:

```sh
docker compose cp api:/app/output ./local-output
```

Python-зависимости контейнера зафиксированы в `docker/requirements.lock` для Python 3.12 и Linux x86_64; клиентские — в `client/package-lock.json`.

## Конфигурация и воспроизводимость

Основной шаблон настроек — [`.env.example`](.env.example). Полная таблица переменных с defaults, границами действия и расположением конфигураций: [docs/CONFIGURATION.md](docs/CONFIGURATION.md).

Версии Python и Node.js зафиксированы содержимым базовых Docker-образов по SHA256 digest; nginx и SearXNG также закреплены по digest. Python-зависимости устанавливаются из `docker/requirements.lock` с `--require-hashes`, клиент — через `npm ci` из `client/package-lock.json`. `flake.lock` фиксирует альтернативное окружение Nix, но основным способом приёмки остаётся Docker.

Фиксация не делает живой ML побитово воспроизводимым: apt-пакеты OCR устанавливаются из текущего репозитория Debian, ревизии весов Hugging Face не закреплены, внешние публикации и модель провайдера могут измениться. Синтетический сценарий воспроизводит контрольные ответы; UUID, временные метки и пути артефактов могут отличаться. [Реестр версий и ограничения](docs/REPRODUCIBILITY.md).

## 4. Разработка и проверки

Для редактирования фронтенда с быстрым обновлением используйте Node.js 22. При работающем Docker-приложении запустите в отдельном терминале:

```sh
cd client
npm ci
VITE_PROXY_TARGET=http://127.0.0.1:8080 npm run dev
```

Откройте [dev-сервер](http://127.0.0.1:5173/). Если изменили `APP_PORT`, подставьте его в `VITE_PROXY_TARGET`.

Проверки из корня проекта:

```sh
npm --prefix client ci
npm --prefix client run build
docker compose config --quiet
docker compose exec -T api python -m unittest discover -s server/tests -v
# Отдельный процесс с временной БД, без внешних сервисов.
docker compose exec -T api python -m demo.check_local
```

`npm run build` выполняет проверку архитектуры, TypeScript, клиентские тесты и production-сборку. API-тесты используют временную SQLite и контролируемые ответы ML. Они проверяют интеграцию, но не заменяют реальную генерацию и вопрос в чат из шагов 8–9.
